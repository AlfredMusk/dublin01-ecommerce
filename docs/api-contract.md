# DUBLIN/01 — frontend / backend contract

The storefront is a static frontend. Everything below is what it expects from a
future backend. Nothing here is implemented server-side today: the browser reads
`src/data/products.json` and keeps the bag and wishlist in `localStorage`.

Each row names the single frontend module that has to change when the endpoint
exists. The interface (pages, cards, drawers) calls those modules only.

## Catalogue

| Need | Endpoint (proposed) | Frontend entry point today |
|---|---|---|
| List products | `GET /products?category=&gender=&brand=&size=&color=&sort=` | `getProducts()` in `src/js/data/catalog.js` |
| One product | `GET /products/:slug` | `getProduct(slug)` |
| Categories | `GET /categories` | `getCategories()` |
| Brands with counts | `GET /brands` | `getBrands()` |
| Search | `GET /search?q=&limit=` → `{ query, total, results }` | `search()` in `src/js/data/search-source.js` |

`Product` is documented as a JSDoc typedef at the top of `catalog.js`. Stored
fields: `id, slug, name, brand, category, type, subcategory, gender, style,
price, compareAtPrice, currency, images[], color, colors[], description,
details[], material, care[], sizeSystem, sizes[], inventory{size: units},
collection, badge, isNew, isFeatured, isLimited, createdAt, keywords[]`.

Derived in the browser from `inventory` (`normalise()`), never stored:
`availableSizes[]`, `stock` (`in_stock | low_stock | out_of_stock`), `available`.
A backend may send them directly; `normalise()` is then the place to drop.

Filtering and sorting run in the browser today (`src/js/pages/catalog.js`). With
a large catalogue they move to the query string of `GET /products`; the URL
parameters the pages already use are the proposed parameter names.

Static pages (`products/<slug>.html`, `brands/<slug>.html`) are generated by
`scripts/build-html.mjs` from the same JSON. With a backend they are either
regenerated on publish or rendered by the server; their URLs do not change.

## Bag

| Need | Endpoint (proposed) | Frontend entry point today |
|---|---|---|
| Read bag | `GET /cart` | `getCart()` in `src/js/modules/cart.js` |
| Add / change / remove a line | `POST /cart/lines`, `PATCH /cart/lines/:id`, `DELETE /cart/lines/:id` | `addToCart()`, `setQuantity()`, `removeFromCart()` |

A line is `{ slug, size, qty }`. Name, price and image are always re-read from
the catalogue, never trusted from storage. Quantity is capped by
`inventory[size]` and by `commerce.maxLineQuantity`. The server must re-check
both, and the price, when an order is created.

## Wishlist

`GET /wishlist`, `PUT /wishlist/:slug`, `DELETE /wishlist/:slug`.
Today: a list of slugs in `localStorage` (`src/js/modules/wishlist.js`). On first
sign-in the local list should be merged into the account.

## Authentication and accounts

`POST /auth/login`, `POST /auth/register`, `POST /auth/password-reset`,
`GET /account`, `GET /account/orders`, `GET|POST|PATCH|DELETE /account/addresses`.
Today: forms validate locally and state that accounts are not open
(`src/js/pages/account.js`). No credential is sent or stored anywhere.

## Checkout, orders and payment

| Step | Endpoint (proposed) |
|---|---|
| Delivery options and prices for an address | `POST /checkout/delivery-options` |
| Create the order from the bag | `POST /orders` → order id, totals, VAT breakdown |
| Payment | handled by the payment provider's hosted fields mounted in `[data-payment-mount]`; the frontend never sees card data |
| Confirmation | `GET /orders/:id` and a confirmation email sent by the backend |

Today the checkout collects contact, address and delivery method, shows the
review, and stops: the final button is disabled because `features.onlineOrdering`
is `false` in `src/js/config.js`. Nothing typed in the checkout is stored.

## Other services awaiting a backend

- **Stock**: real-time inventory and reservation during checkout.
- **Newsletter**: provider and double opt-in (`src/js/modules/newsletter.js`).
- **Contact form**: delivery of messages (`src/js/pages/contact.js`).
- **Delivery rates and tax**: `commerce` values in `src/js/config.js` are development values.
- **Cookie consent**: choices are stored in `localStorage` and announced with a
  `consent:change` event; analytics or marketing scripts must wait for it.
- **Content**: hero campaigns (`src/data/campaigns.json`) and navigation
  (`src/data/site.json`) can be served by a CMS with the same shapes.
- **Admin, analytics, email**: not part of the frontend.

## Business information the frontend is waiting for

`src/js/config.js` → `company`: legal name, registered address, CRO number, VAT
number, customer-service email, phone, support hours; `siteUrl` (production
origin, which switches on absolute canonical URLs, `og:url` and `sitemap.xml`).
